# ADR-001: Выбор стека разработки

- Статус: принято
- Дата: 2026-11-02

## Контекст

Разрабатываем веб-сервис заказа такси. Пассажир выбирает тариф, находит
свободного водителя, создаёт заявку, оплачивает поездку и может её отменить.

Что нужно от стека:

- серверное приложение с JSON-API (операции из контракта API, Задание 4);
- веб-интерфейс для пассажира и админ-панель для оператора (`/admin/`);
- реляционная БД;
- интеграция с внешними системами: платёжным шлюзом и SMS-сервисом;
- автоматические тесты и линтер.

Ограничения: учебный проект, небольшая команда, срок — один семестр. Поэтому
важны быстрый старт и минимум ручной «склейки» библиотек.

## Решение

| Часть | Выбор |
|---|---|
| Язык | Python 3.12 |
| Фреймворк | Django 5.2 (версия с долгосрочной поддержкой, LTS) |
| БД | SQLite (разработка), PostgreSQL (эксплуатация) |
| Тесты | встроенный раннер Django (`python manage.py test`) |
| Линтер | ruff |
| Репозиторий | Git + GitHub, Conventional Commits |

## Почему Django

- В комплекте есть ORM, миграции, админ-панель, шаблоны, авторизация и
  тестовый клиент, поэтому не нужно подбирать и стыковать отдельные библиотеки.
- Приложения Django напрямую соответствуют модулям архитектуры
  (`tariffs`, `drivers`, `rides`, `payments`, `accounts`).
- LTS-версия: обновления безопасности выходят весь срок проекта.
- Админ-панель для оператора из схемы архитектуры не нужно писать самим.

## Рассмотренные альтернативы

| Вариант | Почему не выбран |
|---|---|
| Python + Flask | Минимализм: ORM, админку и авторизацию пришлось бы собирать из отдельных библиотек |
| Python + FastAPI | Хорош для чистого API, но нет админки и серверных шаблонов, больше ручной работы |
| Node.js + Express | Та же проблема, что у Flask: разнородный набор библиотек |
| Java + Spring Boot | Мощно, но тяжелее старт и больше шаблонного кода для учебного срока |

## Последствия

Плюсы:

- быстрый старт, единый стек для API, интерфейса и админки;
- модули легко держать независимыми (одно приложение Django — один модуль).

Минусы и риски:

- Django — монолит: следим за границами модулей и не допускаем циклов
  зависимостей между приложениями;
- SQLite и PostgreSQL различаются в деталях, поэтому перед выпуском
  проверяем работу на PostgreSQL;
- для платёжного шлюза и SMS-сервиса понадобятся сторонние клиенты
  (HTTP-запросы), добавим их по мере необходимости.
